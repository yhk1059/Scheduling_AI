# Step 5: ui-period-schedule

## 읽어야 할 파일

먼저 아래 파일들을 읽고 프로젝트의 아키텍처와 설계 의도를 파악하라:

- `/CLAUDE.md`
- `/docs/PRD.md` (J2, J3, J4)
- **`/docs/UI_GUIDE.md`** ("근무표 이름", "기간 작업" 전체(③ 버튼 표, 게스트 확정), "근무 셀", "반복 사용 컴포넌트"의 지난 근무 마지막 며칠 표·최근 4주 부담·배너, "요약 지표", "상호작용 상태", "문구")
- `/lib/wording.ts` (step 2: `scheduleName`, `formatDeviation`, `wardRuleCount`)
- `/lib/store.ts` (`hasUnconfirmedChanges`, `carryOverChanged`, `rosterChangesFor`, `confirm`, `auth`)
- `/components/PeriodWork.tsx`, `/components/ScheduleStep.tsx`, `/components/Stepper.tsx`, `/components/HolidayCalendar.tsx`, `/components/Account.tsx` (`LoginButton`)

## 배경

UX 점검에서 기간 작업 화면은 제목이 날짜 범위뿐이었고, ③에서 근무표를 만든 뒤에도 [생성]이 Primary라 다음 할 일(확정)이 약하게 보였다. 요약은 "해 상태 · 해 있음 · soft 위반", 통계는 "평균 대비 편차 -0.40", 그리드는 "4주 N" 같은 용어였다. 첫 근무표에는 거의 쓰지 않는 이월 붙여넣기가 기본으로 펼쳐져 있었다. step 1에서 게스트 확정이 가능해졌으므로, 확정 직후 저장 안내도 이 화면에서 보여 준다.

## 작업

### 1. 제목과 ① 준비 (`PeriodWork.tsx`)
- 제목: `scheduleName` ("11월 근무표", 페이지 제목) + 날짜 범위(mono 보조) + 상태 배지(`작성 중` / `확정` / `운영 중`).
- 명단 확인: "지난 근무표 이후 2명 추가 · 1명 제외" / "지난 근무표와 명단이 같아요" + 이름 목록 + [병동 설정].
- 지난 근무 마지막 며칠: 지난 확정 근무표가 있으면 읽기 전용 표(보조 문구는 UI_GUIDE). 없으면 접힌 [지난 근무 입력하기 (선택)] Text 버튼, 펼치면 붙여넣기 입력 + 예시 한 줄("이영희 D E N O O" 같은 형식) + [표로 만들기].
- 지난 근무 변경 배너 문구: "지난 근무표가 바뀌어 이어지는 근무가 달라졌어요. 다시 만들면 반영돼요".

### 2. ③ 근무표 (`ScheduleStep.tsx`)
- **버튼은 UI_GUIDE "③ 근무표의 버튼" 표대로** 상태마다 Primary 하나:
  - 만들기 전: [근무표 만들기] + "적용한 규칙과 요청으로 근무표를 만들어요" 한 줄만. 칸 고정 안내("칸을 눌러 근무를 고정하면…")는 근무표가 생긴 뒤에만 보여 준다.
  - 만든 뒤(작성 중): [확정] Primary, [다시 만들기] Secondary, [CSV 받기] Text
  - 확정 후 변경 없음: Primary 없음, [CSV 받기] Secondary, 운영 중 변경 입력 바
  - 확정 후 변경 있음: [다시 확정] Primary, [CSV 받기] Text
  - 진행 중 레이블 "만드는 중…"
- **게스트 확정 배너**: `auth`가 없을 때 [확정]/[다시 확정] 직후 버튼 근처에 주의 배너 "확정했어요. 이 브라우저에만 저장돼 있어요" + [Google로 로그인](`LoginButton`, `supabaseConfigured`가 false면 버튼 없이 문장만). 배너는 그 기간 화면에 머무는 동안 보이고, 닫기 버튼은 두지 않는다(버튼 최대 하나).
- **요약 지표**(UI_GUIDE "요약 지표"): "결과"(`규칙을 모두 지켰어요` / `근무표 없음`), "희망 반영 9/9" + 보조 한 줄, "못 지킨 규칙".
- **그리드**: 오른쪽 열 이름 "최근 4주 나이트", "최근 4주 주말". `history_load`가 비거나 모두 0이면(첫 근무표) 두 열을 그리지 않는다. 나이트 전담 표시는 "나이트 전담".
- **통계 표**: 열 이름을 문구 표대로("주말·공휴일 근무", "최대 연속 근무", "희망 반영률", "평균보다 많은 근무일"(`formatDeviation`), 최근 4주 열은 위와 같은 조건).
- **해 없음 패널과 제안 카드**: "규칙을 모두 지키는 근무표가 없어요" 계열 문구, 제안 카드의 검증 결과 "이렇게 바꾸면 근무표를 만들 수 있어요 · 희망 반영 14/16". "재풀이" 글자를 화면에 남기지 않는다.
- 누적 부담 근거 한 줄은 "이번 근무표에서 나이트를 줄였어요" 표현으로 바꾼다.
- 운영 중 변경 입력 바의 버튼과 placeholder도 문구 표를 따른다.

## 검증 절차

1. 위 AC 커맨드를 실행한다(코드 주석 속 단어는 grep 대상에서 빼도 된다. 화면 글자가 기준).
2. 수동 확인: `npm run dev` → 샘플 → 다음 근무표 ③ → [근무표 만들기] → Primary가 [확정]으로 바뀌는지, 최근 4주 열이 보이는지 → [확정] → 게스트 배너 → 홈에서 운영 중 근무표 열기 → 지난 날짜 잠금과 [CSV 받기]. 빈 병동으로 첫 근무표를 만들 때 최근 4주 열이 없는지도 확인한다. 확인 후 서버를 종료한다.
3. UI_GUIDE 체크: 영역마다 Primary 하나, 배너 버튼 최대 하나, 토스트 없음, 색만으로 구분하지 않음.
4. 결과에 따라 `phases/3-ux/index.json`의 해당 step을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- 로그인 요구 대화상자를 다시 만들지 마라. 이유: 로그인은 권유만 한다(ADR-014 개정).
- 홈, 시작 화면, 카드 컴포넌트를 바꾸지 마라. 이유: step 4·6의 범위다.
- 백엔드 응답 모델을 바꾸지 마라. 이유: 화면 문구만 바꾼다.
- 기존 테스트를 깨뜨리지 마라.
