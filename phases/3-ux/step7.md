# Step 7: landing

## 읽어야 할 파일

먼저 아래 파일들을 읽고 프로젝트의 아키텍처와 설계 의도를 파악하라:

- `/CLAUDE.md`
- `/docs/PRD.md` (**핵심 기능 9 랜딩페이지**, 사용자, 페인 포인트 표)
- `/docs/UI_GUIDE.md` ("디자인 원칙", "AI 슬롭 안티패턴", "레이아웃"의 랜딩, "타이포그래피"의 랜딩, **"문구"**)
- `/app/page.tsx`, `/components/LandingPreview.tsx`
- `/lib/wording.ts` (step 2)
- `/README.md` (기술 설명을 옮길 곳)

## 배경

결정: 랜딩도 수간호사가 읽는다고 보고 쓴다. 지금 랜딩은 "한 달 근무표를 짭니다"(이제 1주~4주도 지원), "LLM이 정해진 템플릿 12개 중 하나로 번역", "hard 규칙/soft 규칙", Pydantic, eval 표처럼 기술 설명이 위쪽 섹션까지 차지한다. PRD 핵심 기능 9가 새 구성을 정했다: **첫 화면 → 문제 → 동작 방식 → 데모 → 만든 방식(맨 아래, 짧게) → 링크.**

## 작업

### 1. `app/page.tsx`
- **첫 화면**: 가치 제안을 근무표 주기에 묶지 않는다. 예: "말로 설명한 규칙으로 근무표를 짭니다". 보조 문장은 수간호사 말투로(LLM, CP-SAT 언급 없이). [근무표 만들기] → `/app`. 아래 한 줄 "로그인 없이 샘플 병동(15명)으로 체험하거나, 내 명단으로 바로 시작할 수 있어요."
- **문제**: 페인 포인트 4~6개(PRD 페인 포인트 표). 해결 설명에서 "재풀이", "규칙 카드로 번역" 같은 용어를 화면 문구 표의 말로 바꾼다. 반복 사용(지난 근무 이어받기, 최근 4주 나이트 배려)을 하나 넣는다.
- **동작 방식**: ① 말로 규칙 적기 → ② 근무표 만들기 → ③ 막히면 이유와 해결책 → ④ 다음 근무표로 이어짐. LLM·CP-SAT·템플릿·hard/soft를 쓰지 않는다.
- **데모**: 자리표시 유지.
- **만든 방식**(맨 아래 섹션 하나, 짧게): "말을 규칙 카드로 바꾸고 설명하는 일은 LLM이, 근무 배정 계산은 CP-SAT 솔버가 합니다" 수준의 문단 1~2개 + eval 결과 한 줄(케이스 수와 제약 F1). 검증 장치 상세와 eval 표는 README로 옮기고 [GitHub에서 자세히 보기] 링크.
- **바닥글**: 포트폴리오 프로토타입 표기, [개인정보처리방침], [GitHub 저장소].

### 2. `components/LandingPreview.tsx`
- 우측 제품 화면 조각의 용어를 앱과 맞춘다: 열 이름 "최근 4주 나이트"/"최근 4주 주말"(좁으면 두 열을 빼도 된다), 카드 토글 "반드시/가능하면", 해석 결과 문장(`lib/wording.ts` 재사용 가능).

### 3. `README.md`
- 랜딩에서 뺀 설계 요약(LLM 출력 검증 장치, eval 표와 회차별 기록)을 README의 적절한 섹션으로 옮긴다. 이미 있으면 중복하지 않는다.

## 검증 절차

1. 위 AC 커맨드를 실행한다.
2. 수동 확인: `npm run dev` → `/` 를 위에서 아래로 읽으며 기술 용어가 "만든 방식" 섹션에만 있는지, 링크 3개(앱, 개인정보처리방침, GitHub)가 동작하는지 확인한다. 확인 후 서버를 종료한다.
3. UI_GUIDE 체크: 중앙 정렬 히어로·그라데이션·장식 이미지·근거 없는 수치 없음, 랜딩은 API를 호출하지 않음.
4. 결과에 따라 `phases/3-ux/index.json`의 해당 step을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- eval 수치를 새로 만들거나 바꾸지 마라. 이유: 실제 측정값만 쓴다(기존 값 그대로 옮긴다).
- 후기, 사용자 수, 시간 절감률 같은 근거 없는 수치를 넣지 마라. 이유: UI_GUIDE 레이아웃 규칙.
- `/app` 화면을 바꾸지 마라. 이유: step 4~6의 범위다.
- 기존 테스트를 깨뜨리지 마라.
