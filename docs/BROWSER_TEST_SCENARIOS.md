# 브라우저 테스트 시나리오

PRD의 데모 저니(최종 수용 기준)를 브라우저에서 확인하는 유저 케이스다.
이 문서를 기준으로 실행 스크립트를 만든다. 그래서 각 단계에 **대상(접근성 역할과 이름)**, **값**, **검증**을 적었다.
범위는 **게스트 모드**까지다(ADR-014). 로그인과 Supabase 저장은 자동화하지 않는다.
범위에서 뺀 것: CSV 다운로드, 로그인.

## 실행 환경
- 실행: `npm run test:e2e` (Playwright, `e2e/`). 서버가 떠 있지 않으면 Playwright가 Next와 FastAPI를 띄운다. 처음 한 번은 `npx playwright install chromium`이 필요하다.
  - `e2e/entry.spec.ts`: S1, S1-b, S2
  - `e2e/operating.spec.ts`: S3, S4 (운영 중인 병동 D3, 하나의 흐름)
  - `e2e/journey.spec.ts`: S5~S13 (처음 설정부터 내 병동 첫 근무표, 하나의 흐름)
  - `e2e/structure.spec.ts`: S14, S15 (근무 형태·태그·시작일, 하나의 흐름)
  - `e2e/expressions.spec.ts`: S16~S18 (식 규칙: v5 저장본, 조건부·짝·값 수정, 말로 병동 소개·사람이 모자란 필요 인원, 하나의 흐름)
  - `e2e/test-helpers.ts`: 공통 도우미(근무표 읽기, 반드시 규칙 검사(따로 구현한 검사 + 식 규칙 평가), 개발 용어 검사)
- 서버: `npm run dev` (Next :3000 + FastAPI :8000). 기준 URL은 `http://localhost:3000`
- `.env.local`에 `ANTHROPIC_API_KEY`가 있어야 한다. 규칙·요청 만들기, 근무표 없음 설명, 운영 중 변경이 실제 API를 부른다(LLM을 mock하지 않는다, ADR-013).
- 저장소: localStorage 키 `nurse-scheduler`. Playwright는 spec마다 새 브라우저 컨텍스트라 비어 있다.
- **시간 고정**: 실행일과 무관하게 같은 날짜가 나오도록 브라우저 시계를 `page.clock.setFixedTime(new Date("2026-10-28T09:00:00+09:00"))`(수요일)로 고정한다. 첫 페이지 이동 전에 건다.
  - translate 요청의 `today`도 클라이언트 시계로 보내므로 함께 고정된다.
  - D3은 이 날짜 기준으로 만든 상태라 10월 근무표가 운영 중, 11월 근무표가 작성 중이다.
- 대기 시간 상한
  - 규칙·요청 만들기(`/api/py/translate`): 30초. 버튼이 "읽는 중…"에서 원래 이름으로 돌아올 때까지 기다린다.
  - 근무표 만들기(`/api/py/solve`): 15초. "만드는 중…"이 사라지고 [근무표 만들기] 또는 [CSV 받기]가 다시 눌릴 때까지 기다린다.
  - 근무표 없음 설명(`/api/py/explain`): 40초. "원인을 분석하는 중…"이 사라질 때까지 기다린다.
- 모든 시나리오 공통 검증
  - 콘솔에 error 레벨 메시지가 없다.
  - `/api/*` 응답이 모두 2xx다.
  - 오류 알림(`role=alert`, [다시 시도] 포함)이 뜨지 않는다.
- 처음 설정·근무표 작성의 단계는 스테퍼 `list "처음 설정 단계"`, `list "근무표 작성 단계"`에서 현재 단계(aria-current=step)로 확인한다. 확정 근무표 화면에는 스테퍼가 없다.
- 해석 결과는 LLM에 따라 조금씩 다를 수 있다. 그래서 카드 문구 전체를 맞추지 않고 **카드 제목(블록 모양의 이름)과 해석 결과의 핵심 낱말**(예: "미드", "1명")만 검증한다. 같은 뜻의 다른 블록 모양(사람마다 한 장 / 여러 사람을 한 장, 나이트 다음 휴무 / 금지 순서)도 통과로 본다.
- **개발 용어 검사**: 표시된 화면에서 `body`의 보이는 글자에 아래가 없다(UI_GUIDE "문구"). LLM이 쓴 문장(근무표 없음 설명, 되묻기)이 있는 화면은 검사하지 않는다.
  - `hard`, `soft`, `해 있음`, `해 없음`, `초안`, `이월`, `기간`, `달력 월`, `생성`, `재풀이`, 간호사 id(`n01` 같은 `n` + 숫자 두 자리)

## 대상 표기
- `button "근무표 만들기"`: 역할이 button이고 접근성 이름이 "근무표 만들기"인 요소
- `textbox "병동 규칙 입력"`: aria-label이 "병동 규칙 입력"인 입력칸
- `text "규칙을 모두 지켰어요"`: 화면에 보이는 텍스트
- `section "11월 근무표"`: 제목(heading)이 "11월 근무표"인 카드(`<section>`)
- **Primary**: 강조색(`bg-[#155E75]`) 버튼. "유일한 Primary"는 `main` 안에 그 버튼 하나만 있다는 뜻이다.
- 근무표 칸: `button "{이름} {M}월 {D}일 {코드}"` (예: `button "김철수 11월 10일 D"`). 코드는 병동의 근무 코드(기본 D/E/N/O, 병동이 더한 M·DE 등)다. 월은 날짜마다 계산한다.
- 지난 근무 마지막 며칠 칸: `[aria-label="{이름} {M}/{D} {코드}"]` (`<div>`, 편집하지 않음)

## 시나리오 진행 순서
S1, S1-b, S2는 각각 독립이다. S3~S4, S5~S13, S14~S15, S16~S18은 각각 앞 시나리오의 상태를 이어받는 **하나의 연속 흐름**이다.

```
S1 ─ 독립   랜딩 → 샘플 데모 → 내 병동
S1-b ─ 독립 앱 바로 열기 → 시작 화면
S2 ─ 독립   시작 화면
S3 → S4     운영 중인 병동(D3 주입): 11월 근무표 작성·확정 → 10월 확정 근무표에서 변경 입력
S5 → … → S13  내 병동: 처음 설정 ①②③ → 첫 근무표(11월) 작성 → 근무표 없음 → 칸 고정 → 확정 근무표 → 다시 들어오기
S14 → S15   근무 형태: 미드 추가·더블·책임 태그 규칙 → 첫 근무표 시작일 15일 → 다음 근무표 시작일 미루기
S16 → S17 → S18  v5 저장본(D6) 열기 → 조건부·짝 규칙·값 수정 → 다시 만들기 → (새 병동 D7) 말로 병동 소개 → 사람이 모자란 필요 인원
```

### D3. 운영 중인 병동 (시계 2026-10-28 기준, `e2e/fixtures/ward-oct.json`)
- 게스트 저장 상태를 localStorage(`nurse-scheduler`)에 넣어 만든다. 앱에는 이 상태를 만드는 기능이 없다(샘플은 보기 전용 데모, ADR-016).
- **옛 저장본(v4)**이다. 규칙은 템플릿 형식이고 나이트 전담은 `night_only`다. 앱이 열 때 v5(ADR-018)를 거쳐 v6(ADR-019)으로 바꾼다: 규칙은 같은 id의 식 규칙(필요 인원·나이트 전담은 `default: true`), 나이트 전담은 태그, 기본 규칙 "나이트 전담은 나이트와 휴무만"을 더한다. 옛 결과는 형식을 바꾸지 않는다.
- 병동 이름 `외과 병동`, 명단 D1, 필요 인원 D2, 근무표 주기 한 달, 병동 규칙 6개(나이트 다음 휴무, 최대 연속 근무 5일, 최대 연속 나이트 3일, 최소 휴무 8일, 나이트 고르게, 주말·공휴일 고르게). 변환 뒤에는 기본 규칙을 더해 7개로 센다
- **10월 근무표** `2026.10.1 – 10.31`: 확정(운영 중), 마지막 확정 9/30 18:00, 공휴일 없음
  - 지난 날짜: 10/1~10/27 (오늘 10/28은 잠기지 않음)
- **11월 근무표** `2026.11.1 – 11.30`: 작성 중, 요청 3개 적용됨
  - 이영희 11/10~11/12 휴가, 박민수 주말·공휴일 나이트 피하기, 정유진 11/20 데이 희망
  - 지난 근무 마지막 며칠: 10/25~10/31 (7일)
  - 최근 4주 창: 11월 직전 28일(10/4~10/31)의 확정본

## S1. 랜딩 → 샘플 데모 → 내 병동
**사전 상태**: localStorage를 비운다.

| # | 동작 | 대상 | 값 |
|---|---|---|---|
| 1 | 이동 | `/` | |
| 2 | 확인 | `heading` (h1) | "말로 설명한 규칙으로 근무표를 짭니다" (줄바꿈 무시) |
| 3 | 확인 | `link "샘플로 체험하기"`, `link "내 병동으로 시작하기"` | href=`/demo`, `/app?start=new` |

**검증**
- 1~5 동안 `/api/*` 요청이 하나도 없다(랜딩과 데모는 정적).
- 샘플(`lib/samples/ward-15.json`)은 식 규칙 형식이다(옛 블록을 `backend/domain/convert.py`의 `block_to_rules`로 기계 변환, 필요 인원·나이트 전담은 `default: true`. 근무 형태 기본값, 나이트 전담 태그 포함). 데모의 규칙 카드 문장과 랜딩 조각은 같은 샘플을 `describeRule`로 그린다(조정 가능한 값은 밑줄). 데모 근무표(`demo-schedule.json`)는 `npm run gen:demo`로 같은 규칙을 풀어 둔 것이다. 랜딩은 지나간 뒤에도 숨겨진 채 DOM에 남을 수 있어 원문은 `main` 안에서 찾는다.
- 5에서 localStorage에 `nurse-scheduler` 키가 없다(데모는 저장하지 않는다).
- 개발 용어 검사(샘플 데모).

## S1-b. 앱을 바로 열면 시작 화면
**사전 상태**: localStorage를 비운 뒤 `/app`으로 간다.

**검증**
- `heading "시작 방법"`이 보인다.
- 시작 화면 카드는 2개(`main`의 h2 2개)다: `link "샘플로 체험하기"`(href=`/demo`), `button "내 병동으로 시작하기"`. `button "이어서 하기"`가 없다(저장된 입력 없음).
- `main` 안에 로그인 카드나 `button "Google로 로그인"`이 없다(로그인은 상단 바에만 있다).
- 시작 화면에서는 `button "근무표"`, `button "병동 설정"` 탭이 없다.
- 개발 용어 검사(시작 화면).

## S2. 시작 화면과 입력 삭제 확인
**사전 상태**: localStorage를 비운 뒤 `/app`으로 간다.

| # | 동작 | 대상 | 값 |

### S6-a. 규칙 만들기와 적용
| # | 동작 | 대상 | 값 |

**검증: 근무표가 반드시 규칙을 지키는지**
칸 버튼의 aria-label `^(.+) (\d+)월 (\d+)일 ([A-Z0-9]{1,3})$`을 읽어 `이름 → 날짜별 코드 배열`을 만들고, 마지막 `/solve` 요청의 제약(꺼진 것과 '가능하면' 제외)에 대어 확인한다.

| ID | 규칙 | 조건 |
|---|---|---|
| H1 | 필요 인원 | 날짜마다 D/E/N 인원이 D2 범위 안에 있다. 주말·공휴일 날짜는 D3·D4 |
| H2 | 나이트 다음 휴무 | N 다음 날은 N 또는 O다(N 다음 날에 D/E가 없다). R1이 금지 순서로 해석됐다면 해당 순서만 확인한다. 지난 근무 마지막 며칠이 있으면 근무표 경계도 본다 |
| H3 | 연속 나이트·연속 근무 | 연속 N이 상한 이하, 연속 근무가 상한 이하다(지난 근무 마지막 며칠 포함) |
| H4 | 연차별 배치 | 날짜·근무마다 3년차 이상이 1명 이상이다 |
| H5 | 휴가 | 휴가 날짜가 O다 (내 병동: 이영희 15~17일) |
| H6 | 나이트 전담 | 문가람·배수아에게 N/O만 있다 |
| H7 | 고정 | 고정 근무(칸 고정, 지난 날짜 잠금)가 그대로다. 최소 휴무 일수도 함께 본다 |
| H8 | 식 규칙 평가 | 모든 반드시 규칙(조건부·짝 등 H1~H7이 읽지 못하는 모양 포함)을 백엔드 식 평가(`solver/evaluate`)로 센 위반이 0이다. 근무표 칸을 모두 고정 근무로 걸고 반드시 식 규칙을 가능하면으로 바꿔 `/api/py/solve`에 보내면 응답의 `soft_violations`가 그 평가 결과다(반드시 고르게 규칙은 그대로 두고 해가 있어야 한다) |

- 첫 근무표에는 확정한 지난 근무표가 없으므로 `history_load`가 비어 있고, "최근 4주" 열과 근거 한 줄이 화면에 없다.
- 개발 용어 검사(② 근무표).
