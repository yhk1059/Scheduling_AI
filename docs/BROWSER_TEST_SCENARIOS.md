# 브라우저 테스트 시나리오

PRD의 데모 저니(최종 수용 기준)를 브라우저에서 확인하는 유저 케이스다.
이 문서를 기준으로 실행 스크립트를 만든다. 그래서 각 단계에 **대상(접근성 역할과 이름)**, **값**, **검증**을 적었다.
앱은 로그인이 필요하다. e2e는 테스트 Supabase 프로젝트의 전용 계정으로 로그인한다(ADR-020). Google 로그인 자체는 자동화하지 않는다.
범위에서 뺀 것: CSV 다운로드, Google 로그인 과정(로그인 화면의 버튼까지만 본다).

## 실행 환경
- 실행: `npm run test:e2e` (Playwright, `e2e/`). 서버가 떠 있지 않으면 Playwright가 Next와 FastAPI를 띄운다. 처음 한 번은 `npx playwright install chromium`이 필요하다.
  - `e2e/entry.spec.ts`: S1, S1-b, S2
  - `e2e/operating.spec.ts`: S3, S4 (운영 중인 매장 D3, 하나의 흐름)
  - `e2e/journey.spec.ts`: S5~S13 (매장 준비부터 직원 입력과 첫 근무표까지, 하나의 흐름)
  - `e2e/structure.spec.ts`: S14, S15 (시작일·근무 형태·태그, 하나의 흐름)
  - `e2e/expressions.spec.ts`: S16~S18 (식 규칙: 저장된 매장 열기, 조건부·짝·값 수정, 말로 적는 매장 조건·사람이 모자란 필요 인원, 하나의 흐름)
  - `e2e/test-helpers.ts`: 공통 도우미(테스트 계정 로그인, 저장 상태 준비, 토큰 DB 함수로 가능 시간 제출, 근무표 읽기, 반드시 규칙 검사(따로 구현한 검사 + 식 규칙 평가), 개발 용어 검사)
- 서버: `npm run dev` (Next :3000 + FastAPI :8000). 기준 URL은 `http://localhost:3000`
- `.env.local`에 다음이 있어야 한다.
  - `ANTHROPIC_API_KEY`: 규칙·요청 만들기, 근무표 없음 설명, 운영 중 변경이 실제 API를 부른다(LLM을 mock하지 않는다, ADR-013).
  - `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`: **테스트 Supabase 프로젝트**의 값. 운영 프로젝트를 가리키면 안 된다.
  - `E2E_TEST_EMAIL`, `E2E_TEST_PASSWORD`: 테스트 전용 계정. 값은 문서와 저장소에 적지 않는다.
- `NEXT_PUBLIC_E2E_LOGIN=1`은 `.env.local`에 두지 않는다. Playwright가 띄우는 Next 서버에만 켠다(`playwright.config.ts`). 이 값이 없으면 테스트 로그인 경로가 없다(ADR-020). 이미 떠 있는 개발 서버는 재사용되므로 이 값 없이 띄운 서버를 끄고 실행한다.
- **로그인**: 도우미 `loginAsTestUser(page)`가 테스트 로그인 경로로 세션을 만든다. S1, S1-b와 직원 화면은 로그인하지 않은 컨텍스트로 연다.
- **저장 상태 준비**: 도우미가 테스트 계정으로 로그인한 supabase-js(RLS)로 그 계정의 `shops` 행과 `availability_links` 행을 지우고 넣는다. service role 키는 쓰지 않는다. 각 흐름의 **사전 상태**에서 "계정을 비운다"는 이 삭제를 뜻한다.
  - 계정이 하나라 spec은 차례로 돌린다(`workers: 1`).
- **가능 시간 제출 도우미**: `availability_links`에서 직원의 토큰을 읽어(RLS) `submit_availability(토큰, 칸)`을 anon으로 부른다. 직원 화면을 거치지 않는다.
- **시간 고정**: 실행일과 무관하게 같은 날짜가 나오도록 브라우저 시계를 `page.clock.setFixedTime(new Date("2026-10-28T09:00:00+09:00"))`(수요일)로 고정한다. 첫 페이지 이동 전에 건다. 직원 화면 컨텍스트도 같다.
  - translate 요청의 `today`도 클라이언트 시계로 보내므로 함께 고정된다.
  - D3은 이 날짜 기준으로 만든 상태라 10/5~11/1 근무표가 운영 중, 11/2~11/29 근무표가 작성 중이다.
- 대기 시간 상한
  - 규칙·요청 만들기(`/api/py/translate`): 30초. 버튼이 "읽는 중…"에서 원래 이름으로 돌아올 때까지 기다린다.
  - 근무표 만들기(`/api/py/solve`): 15초. "만드는 중…"이 사라지고 [근무표 만들기] 또는 [CSV 받기]가 다시 눌릴 때까지 기다린다.
  - 근무표 없음 설명(`/api/py/explain`): 40초. "원인을 분석하는 중…"이 사라질 때까지 기다린다.
- 모든 시나리오 공통 검증
  - 콘솔에 error 레벨 메시지가 없다.
  - `/api/*` 응답이 모두 2xx다.
  - 오류 알림(`role=alert`, [다시 시도] 포함)이 뜨지 않는다.
- 근무표 작성의 단계는 스테퍼 `list "근무표 작성 단계"`(가능 시간, 매장 조건, 근무표)에서 현재 단계(aria-current=step)로 확인한다. 매장 준비와 확정 근무표 화면에는 스테퍼가 없다.
- 해석 결과는 LLM에 따라 조금씩 다를 수 있다. 그래서 카드 문구 전체를 맞추지 않고 **카드 제목(식 모양의 이름)과 해석 결과의 핵심 낱말**(예: "피크", "1명")만 검증한다. 같은 뜻의 다른 식 모양(사람마다 한 장 / 여러 사람을 한 장)도 통과로 본다.
- **개발 용어 검사**: 표시된 화면(직원 화면 포함)에서 `body`의 보이는 글자에 아래가 없다(UI_GUIDE "문구"). LLM이 쓴 문장(근무표 없음 설명, 되묻기)이 있는 화면은 검사하지 않는다.
  - `hard`, `soft`, `해 있음`, `해 없음`, `초안`, `이월`, `기간`, `달력 월`, `생성`, `재풀이`, `availability`, `토큰`, 직원 id(`e01` 같은 `e` + 숫자 두 자리)

## 대상 표기
- `button "근무표 만들기"`: 역할이 button이고 접근성 이름이 "근무표 만들기"인 요소
- `textbox "매장 조건 입력"`: aria-label이 "매장 조건 입력"인 입력칸
- `text "규칙을 모두 지켰어요"`: 화면에 보이는 텍스트
- `section "11/2~11/8 근무표"`: 제목(heading)이 "11/2~11/8 근무표"인 카드(`<section>`)
- **Primary**: 강조색(`bg-[#155E75]`) 버튼. "유일한 Primary"는 `main` 안에 그 버튼 하나만 있다는 뜻이다.
- 근무표 칸: `button "{이름} {M}월 {D}일 {코드}"` (예: `button "김철수 11월 3일 A"`). 코드는 매장의 근무 코드(기본 A/M/C/O, 매장이 더한 P·AC 등)다. 월은 날짜마다 계산한다.
- 지난 근무 마지막 며칠 칸: `[aria-label="{이름} {M}/{D} {코드}"]` (`<div>`, 편집하지 않음)
- 직원 화면 가능 시간 칸: `button "{M}월 {D}일 {시작}~{끝}"` (예: `button "11월 3일 12:00~12:30"`). 칠한 칸은 aria-pressed=true다.

## 시나리오 진행 순서
S1, S1-b, S2는 각각 독립이다. S3~S4, S5~S13, S14~S15, S16~S18은 각각 앞 시나리오의 상태를 이어받는 **하나의 연속 흐름**이다.

```
S1 ─ 독립   랜딩 → 샘플 데모 → 로그인 → 매장 준비
S1-b ─ 독립 앱을 로그인 없이 열기 → 로그인 화면
S2 ─ 독립   매장 준비: 저장, 로그아웃과 다시 로그인
S3 → S4     운영 중인 매장(D3 준비, 4주 주기): 11/2~11/29 근무표 작성·확정 → 10/5~11/1 확정 근무표에서 변경 입력
S5 → … → S13  내 매장(기본 1주 주기): 매장 준비 → ① 가능 시간(링크 복사, 직원 입력) → ② 매장 조건 → ③ 근무표 → 근무표 없음 → 칸 고정 → 확정(링크 잠김) → 다시 들어오기
S14 → S15   한 달 주기: 시작일 15일 → 피크·더블·리더 태그 규칙 → 근무표 → 다음 근무표 시작일 미루기
S16 → S17 → S18  저장된 매장(D3) 열기 → 조건부·짝 규칙·값 수정 → 다시 만들기 → (새 매장 D6) 말로 매장 조건 → 사람이 모자란 필요 인원
```

### D2. 근무조별 필요 인원 (샘플 매장 `lib/samples/shop-12.json`과 같은 값)

| 근무 | 평일 | 주말·공휴일 |
|---|---|---|
| 오픈 | 1 ~ 2 | 2 |
| 미들 | 1 ~ 2 | 2 |
| 마감 | 3 | 3 |

입력칸은 칸마다 최소·최대 두 개다: `textbox "{평일|주말·공휴일} {오픈|미들|마감} 최소 인원"`, `"… 최대 인원"`. 예: `textbox "평일 오픈 최소 인원"`. 최소와 최대가 같으면 정확히 그 인원이고, 최대를 비우면 "이상"이다. 근무표 작성 ②에서는 접힌 `button "숫자로 입력하기"`를 펼쳐야 보인다.
- 평일 최소 합계는 1 + 1 + 3 = 5명, 주말·공휴일은 2 + 2 + 3 = 7명이다.
- 평일 오픈 + 미들의 최소는 2명이라, "12시부터 15시까지는 최소 3명"(S8의 R4)을 넣으면 평일에 실제로 제약이 더해진다. 그때 평일 최소 합계는 3 + 3 = 6명이다.

### 가능 시간 "전일"
별도로 적지 않은 직원의 가능 시간이다. 근무표의 모든 날 09:00~23:00, 하루 28칸(30분 칸). A, M, C와 P 피크를 모두 덮는다. 직원 화면의 하루 칸은 06:00~24:00, 36칸이다.

### D3. 운영 중인 매장 (시계 2026-10-28 기준, `e2e/fixtures/shop-oct.json`)
- 도우미가 테스트 계정의 `shops` 문서 1행과 `availability_links` 24행(근무표 2개 × 직원 12명)을 넣어 만든다. 토큰은 넣을 때 새로 만든다. 앱에는 이 상태를 만드는 기능이 없다(샘플은 보기 전용 데모, ADR-016).
- 현재 형식의 저장 문서다. 모든 규칙이 식 규칙(`type: "rule"`)이고 필요 인원 6개(`cov-*`)만 `default: true`다. 근무 형태는 기본값이다.
- 이월과 최근 4주를 한 번에 검증하려고 **근무표 주기를 4주**로 둔다. 11/2~11/29의 최근 4주 창이 지난 근무표 전체와 같다.
- 매장 이름 `성수 카페`, 명단 D1, 필요 인원 D2, 근무표 주기 4주, 매장 조건 7개(마감 다음 날 오픈 금지, 최대 연속 근무 5일(`rule-max-run`), 주 최대 근무 40시간, 주 최소 휴무 2일, 오픈에 리더 1명, 마감 고르게, 주말·공휴일 고르게)
- 저장된 규칙은 13개다(필요 인원 6 + 매장 조건 7). 화면의 조건 수에는 필요 인원을 넣지 않아 7개로 센다.
- **10/5~11/1 근무표** `2026.10.5 – 11.1` (28일, 12명 × 28일 = 336칸): 확정(운영 중), 마지막 확정 10/2 18:00, 공휴일 없음
  - 지난 날짜: 10/5~10/27, 23일 (오늘 10/28은 잠기지 않음). 잠기는 칸은 12명 × 23일 = 276개, 남은 칸은 12명 × 5일 = 60개
  - 확정본에 요청(없음)과 배정이 들어 있다.
  - 최지훈의 10/28은 M이다.
  - 링크 12행은 잠겨 있고, 가능 시간은 모두 전일(사람당 28칸 × 28일 = 784칸)이다.
- **11/2~11/29 근무표** `2026.11.2 – 11.29` (28일): 작성 중, 공휴일 없음, 요청 3개 적용됨
  - 이영희 11/10~11/12 휴가, 박민수 주말·공휴일 마감 피하기, 정유진 11/20 오픈 희망
  - 링크 12행은 열려 있고, 가능 시간은 모두 전일(784칸)로 제출돼 있다.
  - 지난 근무 마지막 며칠: 10/26~11/1 (7일, 12명 × 7일 = 84칸)
  - 최근 4주 창: 직전 28일(10/5~11/1)의 확정본
  - 주말 날짜: 7, 8, 14, 15, 21, 22, 28, 29일

### D5. 근무 형태를 바꾸는 매장 (S14, S15)
- 매장 이름: `연남 카페`, 근무표 주기: 한 달(1일~말일, S14에서 고른다)
- 명단 D1
- 가능 시간: 12명 모두 전일(사람당 28칸 × 30일 = 840칸). 시작일을 정한 뒤 제출 도우미로 넣는다.
- 근무 형태: 기본 A/M/C + **P 피크** 11:00~14:00, 실근무 3시간(근무표 작성 ②에서 추가) + 말로 더한 **더블**(A와 C를 세는 코드, LLM이 고른 이름. 보통 `AC`)

| # | 입력 | 기대 카드 제목 (하나) | 해석 결과 핵심 | 토글 |

- `group "반드시/가능하면"` 안에서 기대 토글 버튼이 aria-pressed=true다.

R4의 따로 검증(시간대 필요 인원, ADR-020):
- `/translate` 응답의 규칙이 날마다 세는 규칙이고, 근무 셀렉터가 12~15시를 덮는 코드 **정확히 {A, M}**이며 최소가 3이다. C(17:00 시작)와 O가 들어 있으면 실패다.
- 카드 문장에 "마감"이 없다.

| H8 | 식 규칙 평가 | 모든 반드시 규칙(조건부·짝 등 H1~H7이 읽지 못하는 모양 포함)을 백엔드 식 평가(`solver/evaluate`)로 센 위반이 0이다. 근무표 칸을 모두 고정 근무로 걸고 반드시 식 규칙을 가능하면으로 바꿔 `/api/py/solve`에 보내면 응답의 `soft_violations`가 그 평가 결과다(반드시 고르게 규칙은 그대로 두고 해가 있어야 한다) |

- 11/5는 M, O 중 하나다(A와 C가 없다).
- `/solve` 요청에 `avail-`로 시작하는 규칙이 있고, 저장된 매장 조건에는 없다.

## S10. 근무표 없음 → 설명과 검증된 제안 (데모 저니 5)
**사전 상태**: S9 끝. 예외 입력은 펼쳐 둔다.

| # | 동작 | 대상 | 값 |
|---|---|---|---|
| 1 | 만들기·적용 | `textbox "예외 입력"` | `이영희, 김철수, 정유진, 최지훈 11월 6일 휴가` |
| 2 | 만들기·적용 | `textbox "예외 입력"` | `강서연, 임하늘, 한소율 11월 6일 휴가` |
| 3 | 확인 | `status` | "입력이 바뀌었어요. 다시 만들어 주세요"와 `button "다시 만들기"` |
| 4 | 클릭 | 그 배너의 `button "다시 만들기"` | 완료와 설명 완료까지 대기 |
| 5 | 확인 | 결과 패널 | "근무표 없음" 배지, "규칙을 모두 지키는 근무표가 없어요" |
| 6 | 확인 | 설명 | 설명 문단이 비어 있지 않다 |
| 7 | 확인 | `heading "함께 지킬 수 없는 규칙"` 목록 | 1개 이상. 매장 조건·요청 행에는 `button "이번 근무표에서만 끄기"`가 있다. "{이름} 가능 시간" 행(예: "박민수 가능 시간")이 있으면 그 행에는 이 버튼이 없다 |
| 8 | 분기 | 제안 카드(배지 "검증됨") | 있으면 8-a, 없으면 8-b |
| 8-a | 클릭 | 첫 제안 카드의 `button "수락"` | 다시 만들기 완료까지 대기 |
| 8-b | 클릭 | 11/6 휴가 행의 `button "이번 근무표에서만 끄기"` | 다시 만들기 완료까지 대기. 아직 없으면 반복 |
| 9 | 확인 | 요약 | "규칙을 모두 지켰어요", 결과 패널 사라짐 |

**설계 근거**
- 11/6은 평일(금요일)이고 공휴일이 아니다. 필요 인원 최소 합계는 오픈 1 + 미들 1 + 마감 3 = 5명이다(R4를 더하면 6명).
- 모두 제출한 가능 시간으로 보면, 11/6에 근무조를 덮는 사람은 박민수를 뺀 11명이다(박민수는 그날 칠한 칸이 없다). 나머지 11명은 전일이라 A, M, C를 모두 덮는다.
- 1, 2의 휴가 7명까지 빼면 11 − 7 = 4명(윤지민, 오민준, 서예린, 신도윤)만 남는다. 4명 < 5명이라 근무표가 반드시 없다.
- 남는 4명에 리더 윤지민이 있어 "오픈에 리더 1명"은 원인이 아니다. 부족의 이유는 인원 합계 하나다.
- 충돌을 최소로 추리는 방식에 따라 "박민수 가능 시간"은 목록에 나올 수도, 나오지 않을 수도 있다. R4까지 쓰면 휴가 7명만으로도 충돌이 되기 때문이다. 그래서 7은 행이 있을 때만 본다.
- 가능 시간은 끌 수 없으므로 8-b는 휴가 행만 끈다. 2명을 풀어야(6명) R4까지 채울 수 있다. 한 문장이 사람별 휴가 카드 여러 장으로 나뉘어도, 여러 사람을 한 장(사람 n명 × 11/6 × 휴무 말고 0번)으로 묶어도 정상이다. 생긴 카드는 [모두 적용]으로 모두 적용한다.

**검증**
- 제안 카드에는 "이렇게 바꾸면 근무표를 만들 수 있어요 · 희망 반영 x/y"가 있다.
- 제안 카드의 바꾸는 것은 식에서 만든 한 줄이다: 값 바꾸기 "{값 이름} 3 → 1", "반드시 → 가능하면", "이번 근무표에서만 끄기" 중 하나.
- `/explain` 응답의 제안 중 `avail-` 규칙을 바꾸는 것이 하나도 없다. 제안 카드에 "가능 시간"이 없다.
- 해결 뒤 H1~H7, H9가 성립하고, 이영희 11/3~11/5 휴가는 켜져 있다.
- 어느 분기로 해결했는지 결과에 기록한다.

| 11 | 확인 | 결과 패널 | "근무표 없음" 배지, `heading "함께 지킬 수 없는 규칙"`, 설명 문단이 비어 있지 않다 |
| 12 | 확인 | 제안 카드(배지 "검증됨") | 1개 이상. 값 바꾸기("{값 이름} 9 → n")가 있으면 그것을, 없으면 첫 제안을 고르고 "확인 필요"로 기록 |
| 13 | 클릭 | 고른 제안의 `button "수락"` | "규칙을 모두 지켰어요" |

**설계 근거**
- 평일 오픈 정확히 9명인데 직원은 6명뿐이고, 6명 모두 전일을 제출해 가능 시간은 원인이 아니다. 이 흐름에는 다른 규칙이 없으므로 원인은 이 인원 하나다. 값 바꾸기로 풀면 n은 6 이하다.

**검증**
- 7에서 평일마다 오픈 2명 이상, 주말마다 3명 이상이고 H1~H9가 성립한다. 13 뒤에도 H1~H9.
