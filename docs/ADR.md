# Architecture Decision Records

> ADR-019까지는 간호사 근무표 시절의 기록이라 병동·간호사 용어를 쓴다. 지금 용어와 대체 관계는 ADR-020을 따른다.

## 철학
포트폴리오 프로토타입이다. 데모 저니에 필요한 것만 만든다.
- LLM은 잘하는 것(자연어 이해와 설명)에만 쓰고, 계산과 검증은 결정적 코드로 한다.
- 외부 의존성과 인프라를 최소화한다. 작동하는 가장 단순한 구현을 고른다.

---

### ADR-001: 계산은 CP-SAT, LLM은 번역과 설명만
**결정**: 근무표는 OR-Tools CP-SAT가 푼다. LLM은 자연어 → 제약 스펙 번역과 충돌 설명만 한다.
**이유**: LLM은 조합 최적화에서 제약을 자주 어긴다. 솔버는 해가 없음을 증명하고, 충돌 원인을 찾을 수 있다.
**트레이드오프**: 자체 솔버로 알고리즘 역량을 보여줄 기회를 포기한다(MVP 이후 선택 과제).

### ADR-002: LLM은 템플릿 12개 중에서 고르고 파라미터만 채운다
> ADR-018로 대체됨. 닫힌 스키마로 검증·eval한다는 이유는 유지하고, 템플릿 12개가 범용 블록 3종으로 바뀌었다.

**결정**: 제약 템플릿을 코드로 고정한다. LLM은 tool use로 `type`과 `params`만 출력한다. LLM이 코드를 생성하지 않는다.
**이유**: 출력을 검증할 수 있고, eval로 정확도를 측정할 수 있다.
**트레이드오프**: 템플릿에 없는 규칙은 `unsupported`로 거절한다.

### ADR-003: Pydantic을 단일 기준으로
**결정**: `backend/domain/models.py`에서 tool `input_schema`, 검증, 솔버 입력, `lib/types.gen.ts`를 모두 만든다.
**이유**: 계층마다 스키마가 어긋날 여지를 없앤다.
**트레이드오프**: 타입 생성 스크립트를 하나 유지해야 한다.

### ADR-004: LLM 출력은 검증을 통과한 "제안"으로만 쓴다
**결정**: Pydantic 검증과 참조 무결성 검사를 거치고, 실패하면 최대 2회 재시도한다. 결과는 사람이 [적용]하거나 서버가 재풀이로 검증해야 반영된다. explain이 실패하면 결정적 대체 경로로 간다.
**이유**: 환각이 근무표에 직접 들어가지 않게 한다. 프롬프트 인젝션의 영향도 잘못된 제안 카드에 그친다.
**트레이드오프**: 사용자가 클릭을 한 번 더 해야 한다.

### ADR-005: 백엔드는 무상태, 저장은 클라이언트 localStorage
> ADR-014로 대체됨. 백엔드 무상태 원칙은 유지하고, 저장 위치만 바뀌었다.

**결정**: DB 없이 Zustand + persist를 쓴다. 매 요청에 병동, 제약, 이전 해를 통째로 보낸다.
**이유**: 서버리스와 잘 맞고, 재스케줄과 재현이 단순하다. 인프라가 필요 없다.
**트레이드오프**: 공유 링크와 다중 기기 동기화가 안 된다(MVP 이후 Supabase 선택 과제).

### ADR-006: `solver/`와 `llm/`은 서로 import하지 않는다
**결정**: 둘의 조합(제안 검증 등)은 `routes.py`에서만 한다. 별도 서비스 계층은 두지 않는다.
**이유**: 각각 독립적으로 테스트할 수 있다(솔버는 실제로 돌리고, LLM은 mock).
**트레이드오프**: `routes.py`에 오케스트레이션 코드가 모인다.

### ADR-007: Next.js + FastAPI를 Vercel 프로젝트 하나로
**결정**: `api/index.py`는 진입점만 두고, 앱 코드는 `backend/` 패키지에 둔다. `/api/py/*`는 리라이트한다(개발 중에는 uvicorn :8000으로).
**이유**: 배포 대상이 하나라 단순하다. Vercel은 `api/*.py`를 각각 함수로 만들기 때문에 앱 코드를 `api/` 밖에 둔다.
**트레이드오프**: Python 함수 번들 크기에 여유가 작다(아래 측정 참고).
**검증(0-spike, 2026-10-26)**
- `backend/`가 번들에 포함됨. health와 solve-demo 모두 200
- Python 3.12를 `.python-version`으로 인식
- Linux 기준 의존성 약 218MB(ortools 82MB, numpy 57MB, pandas 46MB) / 한도 약 250MB
- 첫 호출 0.72초(네트워크 포함), 4×7 풀이 7~93ms
- **규칙**: Python 의존성을 추가하지 말 것. 한도를 넘기면 백엔드만 Cloud Run으로 분리한다.

### ADR-008: 동기 요청과 솔버 시간 제한
**결정**: 큐, 웹소켓, 스트리밍 없이 요청과 응답만 쓴다. 솔버는 10초, 충돌 분석은 5초, 제안 검증은 3초 × 3으로 제한한다.
**이유**: 15명 × 31일 규모는 수 초 안에 풀린다. 이 정도로 충분하다.
**트레이드오프**: 큰 병동(40명 초과)은 지원하지 않는다.

### ADR-009: LLM 호출 전 이름 가명화
**결정**: 명단의 성명 전체와, 명단에서 유일한 이름(성 제외)을 `N01` 같은 가명으로 치환해서 보낸다. 치환되지 않은 이름이 출력에 남으면 `clarify`로 처리한다.
**이유**: 개인정보를 최소한으로 내보낸다.
**트레이드오프**: 별명이나 오타가 섞인 이름은 되묻기로 처리해야 한다.

### ADR-010: 도메인 범위 결정
> ADR-020이 나이트 전담과 3교대 전제를 없앤다. ADR-018이 일부를 고쳤다. 근무 코드(3교대 고정), 가중치(상수만), 나이트 전담(솔버 특수 처리) 항목은 ADR-018을 따른다.

**결정**
- **기간**: 병동의 기간 단위(1주 / 2주 / 4주 / 달력 월). ADR-015 참고
- **주말**: 토·일과 사용자가 체크한 공휴일. 인원 기준과 공정성 계산에 모두 적용한다.
- **hard/soft**: 템플릿 기본값을 두고, LLM이 표현 강도로 조정하며, 카드에서 토글할 수 있다. 휴가와 고정 배정은 항상 hard다. 가중치는 상수로만 둔다.
- **나이트 전담**: N/O만 배정하고 나이트 공정성 계산에서 제외한다. 나머지 규칙은 똑같이 적용한다.
- **명단**: 수간호사는 넣지 않는다.
- **날짜 해석**: translator에 실제 오늘 날짜와 대상 기간을 넣는다. eval은 케이스마다 `today`를 고정한다.

**이유**: 한국 병원의 3교대 운영에 맞추면서 범위를 좁힌다.
**트레이드오프**: 3교대 외의 근무 형태와 공휴일 데이터 내장은 지원하지 않는다.

### ADR-011: 모델과 공개 방식
**결정**: 모델은 `claude-sonnet-5-5`로 하고 env `ANTHROPIC_MODEL`로 교체할 수 있게 둔다. 데모는 인증 없이 공개한다. 남용은 Anthropic 콘솔 월 한도, 입력 상한, `max_tokens`로 막는다.
**이유**: 포트폴리오 데모는 접근하기 쉬워야 한다. 서버리스에서 메모리 기반 레이트 리밋은 효과가 없다.
**트레이드오프**: 한도에 걸리면 데모가 503 안내를 띄운다.

### ADR-012: TDD 적용 범위
**결정**: `backend/` 전체와 `lib/`의 순수 함수만 테스트를 먼저 작성한다. UI 컴포넌트와 `lib/api.ts`, `lib/supabase.ts`는 build, lint, 수동 저니로 검증한다. TDD 가드 훅도 이에 맞춰 예외를 둔다.
**이유**: 로직은 테스트로 지키고, UI는 컴포넌트 테스트 비용 대비 효과가 낮다.
**트레이드오프**: UI 회귀는 수동 확인에 의존한다.

### ADR-013: 데모 저니는 Playwright e2e로 수동 실행
**결정**: 데모 저니(`docs/BROWSER_TEST_SCENARIOS.md`)를 Playwright로 자동화해 `e2e/`에 둔다. 개발용 devDependency이고 `npm run test:e2e`로 수동 실행만 한다. `npm run test`와 배포에는 넣지 않는다. LLM을 mock하지 않고 실제 API(`.env.local`의 키)를 쓴다.
**이유**: ADR-012의 수동 저니를 반복해서 같은 방법으로 확인할 수 있다. 실제 LLM과 솔버가 이어지는 흐름을 끝까지 검증한다.
**트레이드오프**: 실행할 때마다 LLM 비용과 수 분의 시간이 들고, LLM 응답에 따라 결과가 흔들릴 수 있다. 컴포넌트 테스트 프레임워크는 여전히 쓰지 않는다.

### ADR-014: 저장과 인증은 Supabase(병동 문서 1개 + RLS)와 Google 로그인, 백엔드는 무상태 유지
**결정**
- **테이블**: `wards(id, owner_id unique, data jsonb, updated_at)` 하나만 둔다.
  - store 상태(병동, 기간, 이력, 확정본 버전)를 문서 하나로 통째로 저장한다.
  - 사용자 1명당 병동 1개다.
- **접근**: RLS는 `owner_id = auth.uid()`다. 브라우저가 supabase-js로 직접 읽고 쓴다. `backend/`는 DB에 접근하지 않는다.
- **인증**: Google OAuth 하나만 쓰고 클라이언트에서만 처리한다. SSR 인증과 미들웨어는 쓰지 않는다.
- **게스트**: 로그인하지 않은 상태는 지금처럼 localStorage에 둔다.
  - 게스트도 확정, 다음 기간, 운영 중 변경을 모두 할 수 있다. 로그인은 요구하지 않고 권한다(상단 바, 확정 직후 저장 안내 배너).
  - 로그인하면 게스트 데이터를 병동 문서로 옮긴다(서버에 병동이 이미 있으면 서버 우선).
  - 처음에는 "확정·다음 기간 만들기 때 로그인 요구"로 정했으나, 게스트 체험이 ③ 근무표에서 끝나 기간 연속성을 보여 줄 수 없어 바꿨다(2026-10-29 UX 점검).
- **동시 수정**: 마지막 저장이 이긴다. `updated_at`을 화면에 보여 준다.
- **정책**
  - 서울 리전을 쓴다.
  - [내 병동 데이터 삭제]는 RLS로 문서를 지운다.
  - 이름 입력란에 이니셜을 써도 된다고 안내한다.

**이유**
- 기간을 반복해서 쓰면 데이터가 누적 자산이 된다. localStorage만으로는 브라우저 삭제나 기기 변경을 견디지 못한다.
- 클라이언트가 전체 상태를 들고 매 요청에 보내는 지금 구조에서는 문서 하나로 저장하는 것이 가장 작은 변경이다. 정규화 테이블, ORM, 부분 동기화가 필요 없다.
- 계산(FastAPI)과 저장(Supabase)이 분리되어 무상태 원칙과 ADR-007(Python 의존성 추가 금지)을 지킨다.
- Google 로그인은 방문자가 가장 적은 클릭으로 저장까지 해 볼 수 있다.

**트레이드오프**
- 서버에서 기간별로 조회하거나 집계할 수 없다. MVP에서는 필요 없다.
- 간호사 이름과 근무 이력을 서버에 보관하는 책임이 생긴다.
- 병원 PC에서 개인 Google 계정을 쓰기 꺼리는 사용자가 있을 수 있다.
- 인증 사용자 자체 삭제는 service role 키가 필요해서 범위 밖이다.
- e2e(ADR-013)는 게스트 모드까지만 자동화한다.

### ADR-015: 근무 기간 모델을 달력 월에서 "시작일 + 길이"로 일반화
> ADR-018이 일부를 고쳤다. 시작일(주 단위 월요일 고정)과 누적 부담 형식(나이트·주말 두 숫자 → 최근 28일 배정 원본)은 ADR-018을 따른다.

**결정**
- **`Period`**: `year/month`에서 `start_date + length`로 바꾼다.
  - 기간 단위는 병동마다 고정한다(1주 / 2주 / 4주 / 달력 월). 주 단위는 월요일에 시작한다.
  - 솔버 내부는 계속 1..N 날짜 인덱스로 다룬다.
- **이월**: 지난 확정본의 마지막 며칠로 클라이언트가 `carry_over`를 자동으로 채운다. 기존 필드를 재사용한다.
- **누적 부담**: 최근 4주의 나이트·주말 근무 요약을 클라이언트가 요청에 담아 보내고, 공정성 목적함수에 반영한다. 백엔드는 무상태를 유지한다.
- **지난 날짜**: 운영 중인 기간에서 오늘 이전 날짜는 기존 고정 배정 제약으로 잠근다. 새 잠금 개념은 만들지 않는다.
- **기간 의존 파라미터**: `min_days_off` 같은 값은 기간당 값으로 정의한다. 기간 단위가 병동마다 고정이라 의미가 흔들리지 않는다.
- **scope**: 제약 `scope`의 `"month"`를 `"period"`로 바꾼다. translate API와 eval 데이터셋도 함께 바꾼다.

**이유**
- 주 단위로 새로 짜는 병동도 대상에 포함한다.
- 기간을 넘어 이월과 공정성을 이어야 반복 사용이 성립한다.

**트레이드오프**
- translator는 날짜를 기간 인덱스로 해석해야 한다. 월 경계를 넘는 기간도 생긴다.
- 기간 길이 상한은 31일로 유지하므로 시간 예산(ADR-008)은 그대로 둔다.
- 기간 단위를 바꾸면 기간 의존 파라미터를 사람이 다시 확인해야 한다.

### ADR-016: 샘플은 저장하지 않는 보기 전용 데모

> ADR-022가 `/demo` 화면을 데모 영상으로 대체했다. 샘플 데이터(`lib/samples/`)는 랜딩 히어로 시퀀스와 시드가 계속 쓴다.
**결정**
- 샘플은 `/demo` 한 화면이다. 모든 방문자에게 똑같이 보이고, 조작할 수 없고, 저장하지 않는다.
- 데이터는 샘플 병동(`lib/samples/ward-15.json`)과 미리 풀어 둔 한 달 근무표(`lib/samples/demo-schedule.json`) 둘뿐이다. 날짜는 고정이고 오늘에 맞추지 않는다.
- 앱(`/app`)과 스토어에는 샘플 개념이 없다. 게스트 입력은 언제나 내 병동이다.
- e2e에서 운영 중·다음 기간 흐름이 필요하면 저장 상태 fixture(`e2e/fixtures/`)를 localStorage에 넣고 시작한다.

**이유**
- 샘플이 게스트의 내 병동과 같은 저장소를 쓰면서 갈림길마다 확인 장치가 붙었다(샘플 표시, 지우기 확인, 로그인 시 샘플 저장 질문). 오늘 기준 날짜를 맞추려고 달 모양 28개를 미리 풀어 둬야 했다.
- 방문자가 알아야 할 것은 "말로 적은 규칙 → 규칙 카드 → 근무표"다. 이건 보기 전용 화면으로 충분히 보여 줄 수 있다.

**트레이드오프**
- 방문자는 이월, 운영 중 변경 같은 반복 사용 기능을 샘플에서 볼 수 없다. 직접 써 보려면 [내 병동으로 시작하기]로 간다.

### ADR-017: 처음 설정과 확정 근무표를 작성 화면에서 분리
**결정**
- **처음 설정**: 근무표를 한 번도 만들지 않은 병동은 안내 단계(병동·명단 → 필요 인원 → 병동 규칙 → [첫 근무표 만들기])로 시작한다. 병동 설정 탭은 그 뒤에 고칠 때만 쓴다.
- **근무표 작성**: 확정 전 기간은 ① 요청 → ② 근무표 두 단계다. ① 준비는 요청 단계 위의 접힌 요약으로 줄인다. 확정은 ②의 끝 버튼이다.
- **확정 근무표**: 확정한 기간은 스테퍼 없는 별도 화면에서 연다. 변경 입력이 맨 위에 있고, 요청 단계로 돌아가지 않는다. [다시 확정] 전에는 [변경 취소]로 마지막 확정본(배정과 요청)으로 되돌린다. 끝난 기간은 보기 전용이다.
- 기간을 열 때 어느 화면인지는 기간 상태로 정한다. 화면 상태(`view`)는 계속 스토어에 둔다. 저장된 옛 `view`는 불러올 때 새 화면으로 바꾼다.

**이유**
- 화면이 기능이 붙는 순서로 자리를 잡아서, 핵심인 "말로 규칙 적기"를 건너뛸 수 있었다(병동 설정의 두 번째 탭).
- 작성(만들기·조정·확정)과 운영(병가 반영·다시 확정)은 시점과 마음가짐이 다른데 한 화면이 상태에 따라 바뀌었다. 가장 급한 병가 입력이 작성용 요소와 섞여 있었다.
- ① 준비는 대부분 확인만 하고 [다음]을 누르는 단계였다.

**트레이드오프**
- 화면 종류가 둘 늘어난다(처음 설정, 확정 근무표). 입력 컴포넌트는 병동 설정·작성 화면과 같은 것을 쓴다.
- [변경 취소]를 위해 확정본 버전에 요청도 남긴다. 요청이 없는 옛 버전에서는 버튼을 숨긴다.
- 첫 근무표의 공휴일 체크가 준비 요약의 [바꾸기]를 한 번 더 눌러야 보인다.

### ADR-018: 제약은 범용 블록 3종, 근무 구조는 병동 설정

> ADR-019가 "블록"과 "LLM" 항목을 대체한다. 블록 3종은 식 언어로 통일되고, 필요 인원은 범위를 받는 기본 규칙이 된다. 병동 구조(복합 코드, 칸마다 코드 하나), 우선순위, 태그, 기간 시작일, 누적 부담은 그대로다.

> ADR-002를 대체한다. ADR-010의 "3교대 고정", "가중치는 상수로만", "나이트 전담" 항목과 ADR-015의 "주 단위는 월요일에 시작"을 고친다.

**결정** (설계: `notes/structure-blocks-design-2026-10-29.md`)
- **병동 구조**: 근무 코드(이름, 시간, 세는 근무조)를 병동이 정한다. 기본값은 D/E/N 8시간 + O. 하루 두 근무는 복합 코드(예: DE = D와 E를 세고 16시간)로 표현하고, 칸마다 코드 하나라는 모델은 유지한다.
- **블록**: 제약은 세기(대상 × 날짜 × 근무를 묶음마다 세어 범위), 순서(금지 패턴, 연속 구간 길이, 구간이 끝난 뒤 휴무), 고르게(사람 사이 차이) 3종과 칸 고정뿐이다. 대상은 사람(명단·연차·태그), 날짜(종류·요일·특정일), 근무(코드 집합 또는 제외 집합)로 고른다. 템플릿 12개는 블록 모양의 이름(카드 제목)으로만 남는다.
- **LLM**: tool use로 블록과 설정 변경만 출력한다. 코드를 생성하지 않는다. Pydantic, 참조 무결성, 빈 대상 검사를 통과한 것만 카드로 제안하고, 사람이 [적용]해야 반영된다(ADR-004 유지). 설정 변경 카드에 딸린 규칙 카드는 함께 적용된다.
- **우선순위**: "가능하면" 규칙마다 중요도 3단계(높음·보통·낮음)를 두고 상수 가중치로 바꾼다. 기본값은 지금 가중치와 같다.
- **명단 태그**: 간호사에 자유 태그를 둔다. 나이트 전담은 태그와 기본 규칙(hard)으로 바꾸고 솔버의 특수 처리를 없앤다.
- **기간 시작일**: 첫 근무표는 아무 날에서 시작할 수 있고(달력 월 단위는 1~28일), 이후는 연속이다. 다음 근무표 시작일은 뒤로만 미룰 수 있다.
- **누적 부담**: 클라이언트는 최근 28일 배정 원본을 보내고, 백엔드가 고르게 블록의 셀렉터로 센다.
- **이전**: 저장 문서 v4는 순수 함수로 v5로 바꾼다. 템플릿은 1:1로 블록이 되고 목적값이 같아야 한다.

**이유**
- 핵심 가치는 수학을 모르는 수간호사가 말로 최적화 문제를 세우는 것이다. 템플릿 고정과 구조 전제(D/E/N/O, 하루 한 근무, 평일/주말, 고정 가중치) 때문에 실제 병동 규칙의 상당수가 말로도 표현되지 않았다.
- 블록 3종은 템플릿 12개를 모두 표현하면서 조합으로 새 규칙(미드 근무, 더블, 주 52시간, 책임 배치, 블록 길이)을 덮는다. 출력이 여전히 닫힌 스키마라 검증과 eval이 가능하다(ADR-002의 이유 유지).
- 템플릿마다 따로 있던 hard·soft·위반 계산 분기가 블록 3종의 것으로 줄어든다.
- 복합 코드는 결과·이월·CSV·표가 칸마다 코드 하나라는 전제를 깨지 않는다.

**트레이드오프**
- LLM 출력 자유도가 커져 정확도 위험이 있다. eval을 의미 기준(무작위 근무표에서 위반이 같은지)으로 바꾸고 새 케이스를 더한다.
- 카드 문장이 일반 문법으로 만들어져 템플릿 문장보다 길 수 있다.
- 휴가가 일반 세기 블록이 되어 schema 수준의 "항상 hard" 보장이 화면 규칙으로 내려간다.
- 하루 세 근무 이상, 사람 사이 짝 규칙, 근무 시각 겹침 계산은 여전히 `unsupported`다.
- 코드 수와 블록 조합에 따라 풀이 시간이 늘 수 있어 입력 상한을 더한다.

### ADR-019: 제약은 제한된 식 언어, LLM은 모델러이자 해설자

> ADR-020이 나이트 전담 기본 규칙과 저장 문서 이전 항목을 없앤다. 식 언어와 LLM 역할은 그대로다.

> ADR-018의 "블록"과 "LLM" 항목을 대체한다. ADR-002의 "닫힌 스키마로 검증·eval한다"는 이유는 유지한다.

**결정** (설계: `notes/expression-rules-design-2026-10-30.md`)
- **식 언어**: 제약은 규칙(`rule`) 하나와 칸 고정뿐이다. 규칙은 범위(`for_each`: 기간·날·사람·사람×날·사람×주·사람×연속 n일) + 본문이다. 본문은 `require`(세기 `count`, 비교, 그리고/또는, 만약 ~면 `when`, 날짜 이동 `offset`) 또는 내장 함수 `balance`(사람 사이 차이)다. 대상 고르기(사람·날짜·근무 셀렉터)는 ADR-018 그대로다. 식은 재귀하지 않는다(조건은 비교 하나, 또는 비교 2~4개의 그리고/또는).
- **LLM 역할**: 말을 식으로 세우는 모델러이자, 충돌을 설명하는 해설자다. tool use로 식(닫힌 JSON 스키마)과 설정 변경만 출력한다. 실행 코드는 생성하지 않는다. Pydantic, 참조 무결성, 빈 대상, 싼 모순 검사를 통과한 것만 카드로 제안하고, 사람이 [적용]해야 반영된다(ADR-004 유지).
- **의미 확인**: 카드 문장은 식에서 결정적으로 만든다(LLM이 쓰지 않음). 서버가 샘플 근무표에서 찾은 위반 사례(≤ 3)를 예시 판정으로 함께 보여 준다.
- **조정 가능한 값**: 식 안의 숫자는 이름과 label이 있는 `values`다. 카드 [수정]과 해 없음 완화 제안은 값, 켜기/끄기, 반드시/가능하면만 바꾼다. LLM은 완화에서 식 구조를 고치지 않는다.
- **기본 규칙**: 필요 인원과 나이트전담은 `기본` 규칙 카드다. 필요 인원은 범위(최소·최대)를 받는다. 처음 설정의 필요 인원은 필수 폼이 아니라 병동 소개 입력(말)과 접힌 숫자 폼이고, 가능 여부는 솔버가 판정한다.
- **유지**: 칸마다 코드 하나, 더블은 복합 코드(ADR-018). 하루 한 근무는 규칙이 아니라 데이터 모델이다.
- **이전**: 저장 문서 v5 → v6을 순수 함수로 바꾼다. 블록은 표대로 식이 되고(금지 패턴이 여럿이면 규칙을 나눈다), 같은 목적값을 내야 한다.

**이유**
- 블록 3종도 정해 둔 틀이라 조건부("신규가 나이트면 책임도"), 짝("둘은 같은 날 나이트 금지"), 세기끼리 비교 같은 실제 병동 규칙이 거절되거나 억지로 끼워졌다.
- 필요 인원 필수 폼과 "정확히 n명", 근무조 합계 경고가 병동 조건을 시스템이 강제했다.
- 실행 코드 생성은 표현력이 가장 크지만 샌드박스, 의미 검증, 규칙 단위 기능(카드, unsat core, 통계, 재스케줄)을 모두 다시 풀어야 한다. 식 언어는 해석만 하므로 안전하고, 근무표 위에서 위반을 계산할 수 있어 카드·충돌 설명·eval이 그대로 산다.

**트레이드오프**
- 출력 공간이 넓어져 그럴듯한 오역 위험이 커진다. 결정적 문장, 예시 판정, 의미 기준 eval, clarify로 줄인다.
- 임의 식은 이름이 없어 충돌 설명과 완화가 블록보다 어렵다. 완화는 값만 움직인다.
- reify 보조 변수로 풀이가 느려질 수 있어 조건 수·offset 폭 상한을 둔다.
- 금지 패턴이 여러 개인 블록은 규칙 여러 개로 나뉜다.
- 근무 시각 겹침, 하루 세 근무 이상, 코드보다 잘게 쪼갠 시간은 여전히 `unsupported`다. 식 언어로 안 되는 규칙이 eval에서 쌓이면 실행 코드 생성을 다시 검토한다.

### ADR-020: 매장 직원 스케줄로 전환하고 근무는 정해진 근무조에서 배정한다

> ADR-010의 "3교대 전제"와 "나이트 전담", ADR-014의 테이블 이름과 "게스트", ADR-013의 게스트 e2e, ADR-018·019의 "나이트 전담"과 "이전" 항목을 대체한다.

**결정** (설계: `notes/shop-pivot-design-2026-10-30.md`)
- **도메인**: 간호사 근무표를 스케줄 근무 매장의 직원 근무표로 바꾼다. 같은 저장소에서 전환하고 간호 버전은 태그 `nurse-final`로 남긴다.
- **근무**: 사용자가 정한 근무조(이름, 시작·끝 시각, 실근무 시간) 중에서 배정한다. 솔버가 시간을 만들지 않는다. 칸마다 코드 하나, 복합 코드는 유지한다. 기본 근무조는 A 오픈, M 미들, C 마감, O 휴무다.
- **시간대 필요 인원**: 그 시간을 덮는 근무조를 세는 규칙으로 표현한다. LLM이 근무조 시각을 보고 코드 집합을 고른다. 식 언어와 솔버는 바꾸지 않는다.
- **이름**: 매장은 `shop`, 직원은 `employee`다. 코드 전체를 바꾼다. Zustand의 `lib/store.ts`와 헷갈리지 않게 `store`를 매장 뜻으로 쓰지 않는다.
- **삭제**: 나이트 전담, 직원의 연차와 연차 셀렉터(경력 구분은 태그), 옛 형식 변환(`legacy.py`, `convert.py`, `lib/migrate.ts`의 v4·v5 변환).
- **흐름**: 스케줄 매니저가 쓰는 서비스다. 근무표마다 ① 가능 시간 → ② 매장 조건 → ③ 근무표 순서다. 요청 단계는 없애고 예외 입력을 ③에 둔다.
- **가능 시간**: 매니저가 직원별 링크를 복사해 공유하면, 직원이 로그인 없이 캘린더를 드래그해 30분 단위로 입력한다. 코드가 근무조 시각과 비교해 반드시 규칙으로 바꾼다. LLM을 거치지 않고 완화 제안 대상이 아니다. 칸 고정은 우선한다. 모두 제출한다고 가정해 미제출 처리를 두지 않는다.
- **로그인**: 앱은 Google 로그인이 필요하다. 게스트 모드를 없앤다. e2e는 테스트 Supabase 프로젝트의 전용 계정으로 로그인한다. 이 경로는 테스트 환경 변수가 있을 때만 켠다.
- **직원 링크 저장**: `availability_links` 테이블에 행마다 추측할 수 없는 토큰을 둔다. anon은 테이블에 접근하지 못하고 토큰을 확인하는 `security definer` DB 함수만 호출한다. `backend/`는 계속 DB에 접근하지 않는다. 직원 화면도 앱처럼 데스크톱 웹 기준이다.
- **노동법**: 판단하지 않는다. 사용자가 말한 규칙만 지킨다.
- **매장 조건**: 병동 소개와 병동 규칙은 해석과 저장이 같아 한 입력창으로 합친다.

**이유**
- 가능 시간은 직원이 가장 정확히 안다. 매니저가 메신저로 모아 옮기는 일이 실제 수고의 큰 부분이다.
- 식 언어와 솔버는 업종에 묶여 있지 않아 대부분 재사용할 수 있다. 실제 사용자, 저장 데이터, 배포가 없어 하위 호환이 필요 없다.
- 정해진 근무조는 지금 데이터 모델과 맞는다. 자유 시간대는 시각 단위 변수가 필요해 솔버를 다시 만들어야 한다.

**트레이드오프**
- 근무조에 없는 시간은 나오지 않는다. 필요하면 근무조를 더한다.
- 시간대 필요 인원이 LLM의 코드 집합 선택에 달려 있어 오역 위험이 있다. 카드 문장, 예시 판정, eval로 확인한다.
- 근무조가 늘면 풀이 시간이 늘 수 있다. 근무 코드 상한 8개는 벤치로 다시 확인한다.
- 로그인 없이는 앱을 체험할 수 없다. 체험은 데모 영상이 맡는다(ADR-022).
- 링크를 가진 사람은 누구나 그 직원의 가능 시간을 바꿀 수 있다. 재발급 기능은 두지 않는다.
- 제출하지 않은 직원은 가능 시간이 없어 어느 칸에도 배정되지 않는다.
- 직원 입력도 데스크톱 웹 기준이라, 링크를 휴대폰으로 열면 드래그를 지원하지 않는다.

### ADR-021: 직원 링크를 근무표당 공용 링크 하나로 바꾼다

> ADR-020의 "직원별 링크"와 "직원 링크 저장" 중 토큰을 직원마다 공유하는 부분을 대체한다.

**결정**
- 매니저는 근무표당 링크 하나를 단체 대화방에 올린다. 직원은 링크를 열어 이름을 고르고 입력한다.
- `availability_shares`에 근무표마다 공용 토큰을 둔다. `availability_links`의 직원 행과 토큰은 내부용으로 유지하고, 가능 시간 읽기와 잠금, `get_availability`, `submit_availability`는 그대로 쓴다.
- anon은 `get_availability_roster(공용 토큰)`로 이름, 직원 토큰, 제출 여부, 매장의 근무조(코드·이름·시각, 휴무·복합 제외)를 읽는다. 칸과 직원 id는 돌려주지 않는다.
- 본인 확인은 두지 않는다. 이미 제출한 이름을 고르면 한 번 더 묻는다.
- 명단에서 빠진 직원의 잠기지 않은 행은 지운다.
- 매니저 화면에 제출 현황을 둔다. 화면에 들어올 때와 [새로고침]에서 읽는다.

**이유**
- 직원마다 링크를 따로 보내는 수고가 없어진다. 메신저로 모아 옮기는 수고를 줄이려는 기능의 취지에 맞다.
- 제출하지 않은 직원은 배정되지 않는데 지금까지 매니저가 이를 볼 수 없었다.
- 소규모 매장에서 PIN이나 로그인은 얻는 안전보다 입력 장벽이 크다.

**트레이드오프**
- 링크를 가진 사람은 누구나 다른 직원 이름으로 입력을 보고 덮어쓸 수 있다. 문제가 되면 첫 제출 때 정하는 PIN을 더한다.
- 링크가 새면 전체 명단이 드러난다. 재발급 기능은 두지 않는다.
- 명단에서 뺀 직원을 같은 근무표에 다시 넣으면 그 직원의 입력은 사라져 있다.
- 단체 대화방 링크는 휴대폰으로 열기 쉽지만 입력은 여전히 데스크톱 기준이다. 모바일 입력은 후속 작업이고, 그때까지 좁은 화면에 PC 안내를 보여 준다.

### ADR-022: 샘플 데모 화면을 데모 영상으로 대체
> ADR-016의 `/demo` 화면을 대체한다.

**결정**
- `/demo`와 `SampleDemo`를 지운다. 랜딩과 로그인 화면의 [데모 영상 보기]가 대화상자로 `public/demo.mp4`를 연다. 페이지 이동, 저장, API 호출이 없다.
- 영상은 실제 앱을 Playwright로 녹화한 것이다. `npm run record:demo`(`scripts/record-demo.ts`)가 e2e 테스트 계정의 매장을 "한강 카페"(현실 시나리오, 영상에서 만들 규칙 하나만 뺀 것)로 시드하고, 직원 링크 → 가능 시간 제출 → 매장 조건 한 줄 → 카드 적용 → 예외 → 근무표 만들기 → 확정을 돌리며 녹화한 뒤 ffmpeg로 mp4를 만든다. 커서는 녹화에 찍히지 않아 스크립트가 가짜 커서를 그린다.
- 화면이 바뀌면 스크립트를 다시 돌려 영상을 새로 만든다. 영상은 저장소에 둔다(2MB 안팎).

> 2026-11-03: 영상을 한강 다이닝 시나리오(`docs/DEMO_SCENARIO.md`)로 바꿨다. `npm run record:dining`(`scripts/record-dining.ts`)이 빈 매장부터 장면 11개를 녹화하고, 대기 구간을 잘라 약 2분 영상을 만든다. 근무표를 만들 수 없다는 결과와 검증된 대안까지 보여 준다.

**이유**
- 정적 샘플 화면은 완성된 근무표 한 장만 보여 주어 핵심인 "말로 적으면 카드가 되고 근무표가 다시 풀린다"를 보여 주지 못했고, 그 움직임은 랜딩 히어로가 이미 맡고 있어 화면이 겹쳤다. "체험하기"라는 이름과 달리 조작도 되지 않았다.
- 샘플 위에 입력 바를 열어 진짜 체험을 만들면 방문자마다 LLM 호출 비용이 들고 남용 제한이 필요하다. 지금 규모에는 녹화가 맞다.

**트레이드오프**
- 영상은 화면이 바뀌면 낡는다. 녹화를 스크립트로 두어 재생성 비용을 낮췄지만, 바뀐 뒤 다시 돌리는 것은 사람이 기억해야 한다.
- 방문자는 직접 눌러 볼 수 없다. 써 보려면 Google 로그인이 필요하다.

### ADR-023: 필요 인원은 "이상"이 기본, 공정성 기본 규칙, 직원의 확정 근무표 열람

> ADR-019의 "기본 규칙"(필요 인원만)에 공정성 기본 규칙을 더한다. ADR-020·021의 직원 링크가 확정 뒤에는 근무표 보기가 된다.

**결정**
- **필요 인원 해석**: "오픈 2명", "최소 3명"처럼 숫자만 말하면 그 인원 이상(`ge`)으로, "정확히", "딱"처럼 같음을 분명히 말할 때만 같음(`eq`)으로 세운다. 카드 [수정]에서 이상/정확히를 바꿀 수 있다.
  - 이미 저장된 규칙은 자동으로 바꾸지 않는다. 대신 새 필요 인원 카드를 적용하기 전에, 켜진 반드시 필요 인원 규칙과 날짜가 겹치고 범위가 만나지 않으면 카드에 충돌을 알리고 [기존 규칙 끄기]를 둔다.
- **공정성 기본 규칙**: 모든 매장에 가능하면 규칙 둘을 `기본`으로 둔다. 최대 연속 근무 5일(`fair-max-run`, 중요도 보통)과 근무 수 고르게(`fair-balance`, 최근 4주 포함, 중요도 낮음). 새 매장과 불러온 매장에 더하고, 같은 id나 같은 모양의 규칙이 있으면 더하지 않는다. 끄면 꺼진 채 남는다. 기본 규칙을 끄는 버튼은 [매장 조건에서 끄기]로 [이번 근무표에서만 끄기]와 구별한다.
- **확정 확인**: [확정]은 "확정하면 직원 링크가 잠겨요" 대화상자를 거친다.
- **직원의 확정 근무표 열람**: 확정한 근무표의 공용 링크에서 이름을 고르면 그 직원의 근무와 전체 근무표를 읽기 전용으로 본다. anon은 `security definer` DB 함수 `get_confirmed_schedule(공용 토큰)`만 호출한다. 이 함수는 `shops.data` 문서에서 그 근무표의 마지막 확정본을 읽어 매장 이름, 날짜, 확정 시각, 공휴일, 근무조, 직원 이름별 근무 코드만 돌려준다. 직원 id와 가능 시간 칸은 돌려주지 않는다. `backend/`는 계속 DB에 접근하지 않는다.

**이유**
- 매니저가 "평일 오픈 2명"이라고 할 때 대부분 최소 인원을 뜻한다. 같음으로 읽으면 사람이 남는 날에도 더 넣지 못해 근무표가 쉽게 없어졌다.
- 저장된 규칙을 몰래 바꾸면 매니저가 정한 조건이 달라진다. 충돌은 적용하는 순간에 보여 주는 편이 원인을 알기 쉽다.
- 매장 조건을 하나도 적지 않아도 연속 근무가 길어지거나 한 사람에게 근무가 몰리지 않아야 첫 근무표가 믿을 만하다. 가능하면 규칙이라 해를 막지 않는다.
- 확정은 직원 링크를 잠가 되돌리기 어렵다(UI_GUIDE "되돌릴 수 없는 동작만 확인").
- 직원은 확정 뒤 근무표를 메신저 캡처로 받아 왔다. 이미 가진 링크로 보면 매니저가 따로 공지할 일이 줄어든다. 확정본은 매장 문서 안에 있으므로 새 테이블 없이 문서에서 읽는다.

**트레이드오프**
- 이전에 "2명"을 같음으로 저장한 규칙은 그대로 남아, 같은 말을 다시 적으면 다르게 읽힌다. 충돌 안내와 [수정]의 이상/정확히로 맞춘다.
- 기본 규칙이 늘어 풀이 결과와 "못 지킨 가능하면 규칙" 수가 이전과 달라진다. 매장 조건 수에도 둘이 더해진다.
- 링크를 가진 사람은 누구나 전체 근무표(이름과 근무 코드)를 본다. 공용 링크와 같은 범위라 따로 막지 않는다.
- DB 함수가 매장 문서의 JSON 모양에 묶인다. 저장 문서 형식을 바꾸면 함수도 함께 바꿔야 한다.
- 잠긴 링크로는 자기가 냈던 가능 시간을 다시 볼 수 없다.

### ADR-024: 공휴일 자동 체크, 요약표는 필요 인원 규칙의 합, 조사는 결정적 후처리, 미제출 안내는 근무표 없음일 때만

> ADR-010의 "공휴일 데이터 내장은 지원하지 않는다"를 고친다. PRD의 "미제출 처리를 두지 않는다"는 유지한다.

**결정**
- **공휴일**: 한국 관공서 공휴일(대체공휴일·선거일 포함)을 `lib/holidays.ts`에 연도별 상수로 둔다(2026~2027년). 외부 API를 부르지 않는다. 새 근무표를 만들 때와 시작일을 미룰 때 그 기간의 공휴일을 자동으로 체크하고, 매니저가 달력에서 고친 값이 최종이다. 저장 문서 모양과 `backend/`는 바뀌지 않는다. 상수에 없는 연도는 자동으로 채우지 않는다.
- **② 요약표**: 근무조·요일 종류 칸의 필요 인원은 켜진 반드시 필요 인원 규칙 중 그 근무조 하나를 세고 그 요일 종류의 모든 날을 덮는 규칙을 합친 값이다(최소는 최댓값, 최대는 최솟값). 폼 규칙과 말로 만든 규칙을 가리지 않는다. 일부 날짜에만 적용되는 규칙은 표에 넣지 않고 카드로만 보인다. 폼으로 넣은 규칙만 카드에서 빠지고, 말로 만든 날마다 규칙은 표와 카드 둘 다에 보인다.
- **조사**: 이름·코드 뒤 조사는 결정적 후처리로 받침에 맞춘다. 화면 문장은 클라이언트 `josa`(`lib/wording.ts`)가, LLM이 쓴 문장은 서버가 가명을 되돌릴 때(`restore`, `backend/llm/pseudonym.py`) 같은 받침 표로 고친다. 숫자와 영문자는 읽는 소리를 따른다(M은 "엠"이라 "M으로"). LLM에게 조사를 맡기지 않는다.
- **미제출 안내**: 근무표가 없고 그 원인이 가능 시간 미제출일 때만(활성 직원 중 제출 0명, 또는 충돌에 걸린 가능 시간 직원이 모두 미제출) 해 없음 패널에 안내 한 줄과 [① 가능 시간으로]만 보여 주고 explain을 부르지 않는다. 근무표가 나오면 미제출을 경고하지 않는다. 확정한 근무표에는 이 분기가 없다.

**이유**
- 매니저가 근무표마다 공휴일을 직접 체크하면 빠뜨리기 쉽고, 빠뜨리면 주말·공휴일 필요 인원이 틀린 채 근무표가 나온다. 공휴일은 해마다 정해져 있어 상수로 충분하고, 외부 API는 무상태·의존성 최소 원칙(ADR-007)과 맞지 않는다.
- 요약표가 폼 값만 보여 주면, 말로 "매일 오픈 1명 이상"을 적용해도 표가 비어 있어 매니저가 조건이 들어갔는지 알 수 없었다.
- 가명을 되돌린 문장과 템플릿 문장에서 "이영희는", "M로 고정" 같은 조사 오류가 보였다. 규칙이 단순하고 결정적이라 코드로 고치는 편이 LLM에 부탁하는 것보다 확실하다.
- 원인이 가능 시간 미제출인데 함께 지킬 수 없는 규칙 목록과 끄기 버튼을 보여 주면 매니저를 규칙을 끄는 쪽으로 이끈다. 원인이 분명하면 LLM 설명 비용도 들 필요가 없다.

**트레이드오프**
- 2028년부터는 상수를 더해야 자동으로 들어간다. 임시공휴일은 발표 뒤에 상수에 더해야 한다.
- 매니저가 뺀 공휴일은 시작일을 미루면 다시 들어올 수 있다(뺀 것을 따로 기억하지 않는다).
- 합친 값의 최소가 최대보다 크면 "3~2명"처럼 그대로 보여 준다. 함께 지킬 수 없다는 것은 드러나지만 따로 경고하지 않는다.
- 받침을 판단할 수 없는 끝 글자(기호 등)면 서버는 LLM이 쓴 조사를 그대로 둔다.
- 일부 직원만 미제출이고 다른 원인이 섞인 충돌은 미제출 안내 대신 기존 패널로 간다.
